# Skills → CC Workflow Studio workflows

Arguments: `$ARGUMENTS`
- empty or `all` → every skill in the project
- one or more skill names → only those
- `--root <dir>` → the project whose `.claude/skills/` to convert (default: the
  git root of the current directory)
- `--force` → overwrite workflow JSON that already exists (default: skip it)
- `--tour` → also add a guided `tour` array to each workflow (costs more; off by default)

CC Workflow Studio has no SKILL.md importer — its Load button only opens
workflow JSON. This skill rebuilds each skill as workflow JSON.

## The round trip — what stays and what is lost

```
SKILL.md ──(this skill, once)──▶ workflow.json ──(IDE Export / ccwf export)──▶ SKILL.md (generated format)
```

- It is **one-way import, then JSON is the source of truth.** After import,
  edit the JSON on the canvas and Export. Never feed an exported SKILL.md back
  into this skill (step 2 skips those).
- Export rewrites SKILL.md as a Mermaid diagram + "Workflow Execution Guide".
  The *wording* changes; the *instructions* must not. Step 5 checks that by
  exporting to a temp folder and diffing against the original.
- Export writes **only** `SKILL.md` (plus `.claude/agents/*.md` for subAgent
  nodes). Other files in the skill folder (scripts, references) are untouched.
- Frontmatter export keeps only: `description`, and from `slashCommandOptions`
  in the JSON: `allowed-tools`, `argument-hint`, `model`, `context`,
  `disable-model-invocation`, `hooks`. Everything else is dropped — `name`
  (Claude Code falls back to the folder name), `user-invocable`, and custom
  keys like `version`, `triggers`, `scope`, `metadata` (Claude Code ignores
  those anyway). Report any dropped key that changes behaviour (e.g.
  `user-invocable: false`).

## 1. Locate the project and the schema

```bash
ROOT=${ROOT_ARG:-$(git rev-parse --show-toplevel 2>/dev/null || pwd)}   # ROOT_ARG = --root, if given
ls "$ROOT"/.claude/skills/*/SKILL.md
# Schema bundled with the extension (newest install wins; Cursor or VS Code)
SCHEMA=$(ls -d ~/.cursor/extensions/breaking-brake.cc-wf-studio-* ~/.vscode/extensions/breaking-brake.cc-wf-studio-* 2>/dev/null | sort -V | tail -1)/resources/workflow-schema.json
```

Only `$ROOT/.claude/skills/` is in scope — not `~/.claude/skills`, not plugins.
If `$ROOT` is your home directory or has no `.claude/skills/`, stop and ask
which project to use (AskUserQuestion: the projects under `~/workplace` that
have `.claude/skills/`, plus "stop"); never fall back to `~`.
If `$SCHEMA` does not exist, continue with the cheat sheet in step 4; for any
node type it does not cover, tell the user the extension isn't installed.

## 2. Build the work list

For each `SKILL.md`, read the frontmatter `name` and `description`, then sort it
into one bucket:

| Bucket | Rule | Action |
|---|---|---|
| **Already a workflow** | `.vscode/workflows/<wf-name>.json` exists | skip unless `--force` |
| **Exported from a workflow** | body starts with a ```` ```mermaid ```` `flowchart` block generated by CC Workflow Studio | skip — its JSON is the source; tell the user to Load that instead (search `.vscode/workflows/` for it) |
| **Reference / knowledge** | no ordered procedure: pattern library, API notes, style guide, checklist of rules (e.g. most `riverpod-*`, `flutter-*` docs skills) | skip — list it in the report as "not procedural" |
| **Procedural** | ordered steps, phases, "if X then Y", questions to the user, delegation | convert |

`<wf-name>` = the skill's **folder name**, lowercased, any char outside
`[a-z0-9_-]` replaced by `-` (workflow names must match `^[a-z0-9_-]+$`).
Export writes to `.claude/skills/<wf-name>/`, so this keeps it pointing at the
original folder. If lowercasing changed the name (e.g. `APP-development-chat-room`),
say so in the report: on macOS's case-insensitive disk it still hits the same
folder, on Linux/CI it would create a second one.

Show the user the buckets (counts + names) before converting. If more than 10
skills will be converted, ask with AskUserQuestion (convert all / only the ones
I name / stop) and write nothing until the answer. An earlier approval in the
conversation counts only if it named this same list; otherwise ask.

## 3. Convert — in parallel for big batches

- ≤ 5 skills: convert them yourself, one at a time.
- More: first ask step 5's IDE question yourself if any workflow is being
  regenerated (agents can't ask the user), and tell the agents it is answered.
  Then spawn `general-purpose` agents with `model: "sonnet"` in one message,
  ~5 skills each. Give
  each agent: the skill paths, `$ROOT`, `$SCHEMA`, the path of this SKILL.md
  with the instruction to follow its steps 4 and 5 exactly (it reads them from
  the file; don't paraphrase them into the prompt), `--tour` if set, and its own scratch
  folder for helper scripts (e.g. `<scratchpad>/wf-batch-<n>/`) — agents
  sharing one folder overwrite each other's scripts. Each agent returns,
  per skill: output path, node count, validation result, and what did not map
  cleanly.
- The agents run in the background: wait until every one has finished before
  step 6. Their reports are not checks — then run step 5a yourself on every
  file they list and confirm each file exists under its name; a missing file,
  a failed validation or an agent that returned no result is ✗ in the report.

## 4. Mapping rules

Read the whole SKILL.md (and skim files it references in its folder) before
mapping. Keep the source language and wording in prompts — the workflow must
still run as a skill after export.

**Nothing may be dropped.** Content that is not a step — background, "when to
use", rules, gotchas, examples, output formats — goes into the prompt of the
node it applies to, or, if it applies to the whole skill, into a first
`prompt` node labelled "Context & rules" right after `start`.

**Code blocks inside any node text must use `~~~` fences, never ```` ``` ````.**
Export wraps each prompt in a ```` ``` ```` block; an inner ```` ``` ```` closes
it early and corrupts the rest of the generated SKILL.md.

**Prefer `prompt` over `subAgent`** unless the source skill explicitly
delegates to an agent/Task — every subAgent node becomes an extra
`.claude/agents/<name>.md` file on export.

| In the skill | Node `type` | Key `data` fields |
|---|---|---|
| entry | `start` (exactly one) | `label: "Start"` |
| exit(s) | `end` (≥ 1, may take many inputs) | `label: "End"` |
| a step the main session does / says | `prompt` | `label`, `prompt` (≤ 10000 chars), optional `variables: {name: ""}` |
| question to the user with 2–4 choices | `askUserQuestion` | `questionText`, `options: [{id, label ≤50, description ≤200}]`, `multiSelect: false`, `useAiSuggestions: false`, `outputPorts` = number of options |
| 2-way condition | `ifElse` | `evaluationTarget` (always — see below), `branches: [{label, condition}, {label, condition}]`, `outputPorts: 2` |
| 3+ way condition | `switch` | `evaluationTarget` (always), `branches` (last one `{label: "default", condition: "Other cases", isDefault: true}`), `outputPorts` = branch count |
| delegated work / Task / "use an agent to…" | `subAgent` | `description` ≤200, `agentDefinition`, `prompt`, `builtInType`: `explore` (search/read code), `plan` (design), `general-purpose` (edit/run), `outputPorts: 1` |
| "use the X skill" (X really exists) | `skill` | `name`, `description` (copied from X's frontmatter, ≤ 1024 chars — cut longer ones to 1021 + `...`), `scope: "project"` or `"user"`, `skillPath` (the real path to X's SKILL.md, project-relative for project skills: `.claude/skills/X/SKILL.md`), `validationStatus: "valid"`, `executionMode` (`"load"` or `"execute"`, chosen per node — see below; add `executionPrompt` ≤ 2000 chars when an executed skill must do only part of its job), `outputPorts: 1` — never invent a skill. The CLI validator rejects a skill node without `skillPath` (`SKILL_MISSING_FIELD`) or with a longer description (`SKILL_DESC_TOO_LONG`). A plugin skill (`plugin:name`) is not a project or user skill: use a `prompt` node that names the command |
| a named MCP tool call | `mcp` | see `$SCHEMA` `nodeTypes.mcp`; if unsure use a `prompt` that names the tool |
| a phase heading grouping steps | `group` (optional) | `label`; children set `parentId` and use positions relative to the group |

### Skill nodes: `load` or `execute`

Export turns the two modes into different instructions, so the choice changes
what runs:

| `executionMode` | Exported as | The main session… |
|---|---|---|
| `"load"` | `skill "X" load-skill-knowledge-into-context-only` | reads X as reference; does **not** run its steps |
| `"execute"` | `skill "X"` (or `skill "X" "<executionPrompt>"`) | runs X's procedure itself, here and now |

Decide per node from the source text, the skill's own content and the
project's policy:

- **`load`** when the source uses X for its rules or facts ("follow X's
  conventions", "look up in X", "see X"), when X is a reference skill (`kn-`
  type, or no procedure), or when X's steps would make changes that the source
  hands to someone else — a delegate (`cursor-agent`, a sub-agent, a spec file
  for another agent) or a hook that blocks the main session's edits (read
  `.claude/settings*.json` hooks and `CLAUDE.md`). The decisions X informs go
  into that hand-off, not into edits here.
- **`execute`** only when the source wants the main session itself to perform
  X's procedure at this point and the project allows it. If only part of X
  should run (e.g. export images but leave `pubspec.yaml` to the delegate),
  say so in `executionPrompt`.
- When unsure, use `load` and say so in the report — reading has no side
  effects, running may.

### Decisions: `evaluationTarget`

Every `ifElse` and `switch` gets `evaluationTarget`: one line naming what is
evaluated ("whether the dialog fetches data", "which `Dialog.md` family the
Figma frame is"). Export prints it as `**Evaluation Target**:` above the
branch conditions; without it the agent only sees the branch labels.

### Conditions and stops written in prose

- **A condition in prose is a branch.** "If …", "when …", "only when …",
  "for any … it needs", "(if needed)", "optional" in the source → an `ifElse`
  (or `switch`) before that step. Never turn a conditional step into an
  unconditional node, and never drop the condition into the prompt text only.
- **A stop in prose is a stop.** "Ask the user", "flag it to the user",
  "wait for approval", "do not continue until …", "stop" → an
  `askUserQuestion` whose options say what happens next (or an `end`), not a
  prompt that merges back into the main path. Merge back only on the option
  that means "continue", and only if the source allows continuing.

Every node: `id` (unique), `type`, `name` (ASCII `[a-zA-Z0-9_-]`, ≤ 50 —
reuse the id), `position: {x, y}`, `data`.

**Connections:** `{id, from, to, fromPort, toPort: "input"}`.
- `fromPort` is `"output"` for start/prompt/subAgent/skill/mcp.
- `askUserQuestion` (single-select), `ifElse`, `switch`: `"branch-0"` …
  `"branch-N"`, one per option/branch, in order; every port connected.
- No self-connections, nothing into `start`, nothing out of `end`; every
  non-start node has an input, every non-end node has an output. Branches may
  merge into a shared next node.

**Layout:** left to right, `x += 300` per step, same `y` for a linear path;
fan branches out by ±175 (2) or −350/0/+350 (3). Return to the parent's `y`
after a merge.

**Paths:** rewrite relative references to files in the skill folder (e.g.
`scripts/run.sh`, `reference.md`) to project paths
(`.claude/skills/<skill-name>/scripts/run.sh`), so they still resolve after the
workflow is exported.

**Top level:**
```json
{
  "id": "workflow-<Date.now()>",
  "name": "<wf-name>",
  "description": "<skill description>",
  "version": "1.0.0",
  "nodes": [...],
  "connections": [...],
  "createdAt": "<ISO now>",
  "updatedAt": "<ISO now>",
  "subAgentFlows": [],
  "slashCommandOptions": {
    "allowedTools": "<frontmatter allowed-tools, verbatim>",
    "argumentHint": "<frontmatter argument-hint>",
    "model": "<frontmatter model>",
    "context": "<frontmatter context>",
    "disableModelInvocation": true
  }
}
```

`description` = the skill's frontmatter description **verbatim** (it drives
when Claude picks the skill). Include only the `slashCommandOptions` keys the
source frontmatter actually has; omit the whole object if it has none.
Frontmatter `hooks` map to `slashCommandOptions.hooks` with the same structure.

With `--tour`: add `"tour": [{order, title, description, nodeIds, languageLesson?}]`
in execution order — an overview step first, ~1 step per node for ≤ 6 nodes,
8–15 steps for bigger workflows; every `nodeIds` entry must be a real node id.

Anything else (limits, node types not listed): check `$SCHEMA` —
`nodeTypes.<type>`, `connections.portNamingRules`, `validationRules`. Max 100
nodes per workflow.

## 5. Write, validate, and round-trip check

Before writing anything, create `$ROOT/.vscode/workflows/originals/` if needed
and back up the original once:
`$ROOT/.vscode/workflows/originals/<wf-name>.SKILL.md` (do not overwrite an
existing backup).

**Regenerating (`--force`, the JSON already exists):** never lose the old
version. Copy the old JSON to
`$ROOT/.vscode/workflows/backups/<wf-name>.<YYYY-MM-DD>.json.bak` (the `.bak`
keeps it out of the Load list), and if `originals/<wf-name>.SKILL.md` differs
from the current SKILL.md, copy it to `backups/<wf-name>.<YYYY-MM-DD>.SKILL.md`
and then refresh `originals/` with the current SKILL.md — the backup must be
the hand-written file Export would replace. Never overwrite a file in
`backups/`; add `-2`, `-3` … instead. Before writing, ask once with
AskUserQuestion whether the workflows being regenerated are closed in the IDE
(closed — continue / skip them / stop): an open editor can save over or rename
the new file (seen: a regenerated file renamed to `<wf-name>-bc.json`).
After writing, list the folder and confirm the file is still there under its
name. If it isn't, look for `<wf-name>*.json` there, report what you found and
ask before renaming anything back.

Write `$ROOT/.vscode/workflows/<wf-name>.json` (2-space indent, UTF-8), then:

**a. Schema** —
```bash
npx -y @cc-wf-studio/cli validate "$ROOT/.vscode/workflows/<wf-name>.json"
```
Must print `is valid`.

**b. Round trip** — export into a throwaway folder (never into the project)
and compare with the original:
```bash
RT=$(mktemp -d)
npx -y @cc-wf-studio/cli export "$ROOT/.vscode/workflows/<wf-name>.json" --cwd "$RT"
# result: $RT/.claude/skills/<wf-name>/SKILL.md
```
Read both files and check, item by item:
- every command, file path, URL, tool/skill/MCP name and code snippet in the
  original appears in the export;
- every condition / branch and every question to the user is present, with
  the same options;
- every conditional phrase in the original ("if", "when", "only when",
  "if needed") sits behind a branch, and every "ask / flag / wait / stop"
  is a question or an end, not a merge;
- every decision shows an `**Evaluation Target**:` line;
- every skill node exports in the mode you chose
  (`load-skill-knowledge-into-context-only` for `load`); no executed skill
  would make changes the source assigns to a delegate or a hook blocks;
- every rule, constraint, example and output format is present;
- no code fence is broken (each node's block in the export closes where the
  next `####` heading starts);
- frontmatter: `description` identical; each supported key carried over;
  unsupported keys listed as dropped. The exported frontmatter must parse as
  YAML: `@cc-wf-studio/cli` 0.2.2 writes `argument-hint` without quotes, so a
  value starting with `[` (e.g. `[--resume-only] [channel names]`) breaks it.
  That is the exporter's bug, not the JSON's — report it next to the workflow
  so the user knows an Export from the canvas needs that line re-quoted.

Fix the JSON and repeat a+b until both pass. Delete `$RT` afterwards. If it
still fails after 3 rounds, delete the new JSON (when regenerating, put the old
one back from `backups/<wf-name>.<YYYY-MM-DD>.json.bak`) and report why — never
leave an invalid or lossy file behind, and never leave a skill that had a
workflow without one.

## 6. Report

A table: skill → workflow file, node count, schema ✓/✗, round trip ✓/✗,
skill nodes as `name (load|execute)`, dropped frontmatter keys, backups
written, notes on anything approximated (including every `load`/`execute`
choice you were unsure about). Then the skipped skills grouped by reason.

Tell the user:
- Open one in Cursor: CC Workflow Studio → **Load** → pick the file.
- **Export overwrites** `.claude/skills/<wf-name>/SKILL.md` with the generated
  format. The original is backed up in `.vscode/workflows/originals/`; commit
  before exporting anyway. Supporting files in the skill folder are left alone.
- From now on edit the **JSON** (canvas) and Export — don't hand-edit the
  exported SKILL.md, or the two drift apart.
